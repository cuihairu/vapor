## 4. Plugin Mechanism Survey (7 References)

The references cover three classes of host: desktop apps (VS Code, Obsidian, Playnite, Heroic), an observability platform (Grafana), and game-platform aggregation (GOG Galaxy), plus ASF, the direct ancestor of vapor's plugin mechanism.

### 4.2 Host-by-Host Takeaways (Judgments Beyond the Table)

**VS Code splits "trust" and "capability" into two separate things.** Capabilities (contributes) are statically readable before activation, so the host knows which UI a plugin will occupy without running its code; trust (Workspace Trust) is a separate, independent axis deciding whether that code may run in the current workspace. The official docs themselves state this boundary does not stop malicious extensions: "Workspace Trust can't prevent a malicious extension from executing code and ignoring Restricted Mode" ([Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust)). Declarative trust's value is not in blocking anyone, but in making "undeclared" mean disabled by default.

**Grafana made "provenance" machine-verifiable.** The signature manifest binds metadata and file digests into a single signature; verification runs at startup, and unsigned plugins are simply not loaded. This is an order of magnitude stronger than "users verify sha256 themselves": digests no longer depend on manual transfer, and provenance and content are verified together ([Plugin signatures](https://grafana.com/docs/grafana/latest/administration/plugin-management/plugin-sign/), Figure 1). Its frontend sandbox is off by default and official plugins are exempt — evidence that even Grafana dares not promise zero-cost compatibility inside a sandbox.

![Grafana Plugin signatures docs (source: https://grafana.com/docs/grafana/latest/administration/plugin-management/plugin-sign/, captured 2026-10-08)](assets/grafana-plugin-sign.png)

**Figure 1** The Grafana signing-mechanism docs page, source text on "verify signatures at startup, tiered signature states". Source: <https://grafana.com/docs/grafana/latest/administration/plugin-management/plugin-sign/>, captured 2026-10-08.

**GOG Galaxy proves process isolation can be made routine.** Each integration is a separate Python process; the host exposes only JSON-RPC methods, dependencies ship with the package, and the host's bundled interpreter is used. The cost is process count and startup overhead; the payoff is that crashes, infinite loops, and dependency conflicts never reach the host.

**Playnite puts its version gate at install time rather than load time.** `RequiredApiVersion` is written in the distribution manifest, so the installer rejects first; at load time it then checks whether SDK references fall within the compatible major version. Two gates — the former blocks users, the latter blocks packaging mistakes. It is also the sample of "no permission model + official risk notice": a red banner at the top of the feature page warns that third-party extensions may cause performance and usability issues (Figure 2).

![Playnite add-ons page (source: https://playnite.link/addons.html, captured 2026-10-08)](assets/playnite-addons.png)

**Figure 2** The Playnite add-ons page: 62 extensions in the Libraries category, with the third-party extension risk notice at the top. Source: <https://playnite.link/addons.html>, captured 2026-10-08.

**ASF is the negative reference frame.** No manifest, no version negotiation, no permissions, no isolation — the cost of those four absences is written in the official wiki: "you can't assume that your plugin once compiled will keep working with all future ASF releases". On the three axes of contract, versioning, and trust, vapor's plugin mechanism fills in exactly what ASF lacks (`docs/plugins.md` §Alignment with ASF).

**Heroic shows what happens without a plugin mechanism.** Extension demand gets pushed back onto the mainline, and the community can only change looks: themes and CSS injection are its only outlet — library logic, store integrations, and the download queue are untouchable. For vapor the lesson is the reverse: a plugin mechanism is not icing on the cake; it decides whether the feature surface can keep expanding.

### 4.3 Patterns Extracted from the Seven

1. Contracts uniformly take the form "manifest file + host API"; the minimal manifest set is id, version, entry point, and capability declarations; none of the seven replaces the manifest with in-code registration.
2. Permissions come in only two flavors: none (Playnite, Obsidian, ASF — leaning on review and reputation), or declarative capabilities plus trust levels (VS Code Workspace Trust, Grafana signature levels). None provides plugins an OS-level capability sandbox.
3. Version compatibility uniformly follows "the host defines the contract, the plugin declares a minimum host version": `engines.vscode`, `RequiredApiVersion`, `minAppVersion`, and `dependencies.grafanaVersion` are isomorphic; ASF is the only one that explicitly promises nothing.
4. Sandboxing done right relies on processes: GOG Galaxy's separate processes, Grafana's standalone backend binaries, VS Code's extension host process. Same-process solutions solve version coexistence and hot unloading, not privilege overreach.
5. The three with central catalogs (VS Code, Grafana, Playnite) all pair automatic updates with risk notices (Figure 3); for the manually placed one (GOG Galaxy), updates depend on people.

## 5. vapor's Plugin Mechanism vs. the References, Dimension by Dimension

**Conclusion**: of the eight dimensions, five are aligned or leading (the inter-plugin dependency graph is something none of the seven references has); isolation is weaker than the three process-based hosts; there are two real gaps — distribution has no update channel, and provenance verification stops at pinned digests. Candidate handling is in §6. Everything in the current-state column comes from `docs/plugins.md`.

## 6. Candidate Improvements (checked items are candidates, not promises; chartering goes by `todo.md`)

- [x] **Install-time reconciliation of index and manifest (effort: low)**. `plugin_install` already reconciles the requested `pluginId`/`version` against the in-package manifest; reconcile `trust`/`permissions`/`apiVersion` as well, to guard against corrupted index entries. Basis: Grafana signs metadata and file digests into the same `MANIFEST.txt`; verifying metadata and content from the same source is standard practice (§4.2). (✅ Landed 2026-10-09 in round 58: catalog mode ships the index declarations as `expectedTrust`/`expectedPermissions`/`expectedApiVersion` with the install directive, the agent reconciles them against the in-package manifest, and disagreements aggregate into one error; see `docs/plugins.md` §Catalog reconciliation)
- [x] **Plugin update-check endpoint (medium)**. Index entries already carry `version`; adding a `plugin_update_check` (index version vs installed version, aggregated per agent) is enough for the CP panel to show "updatable". Basis: the three catalog-based hosts — VS Code, Grafana, Playnite — all have update channels, while vapor today has only install/uninstall/list as actions (§4.1). (✅ Landed 2026-10-09 in round 59: read-only host action `plugin_update_check` + `POST /v1/plugins/update-check`, the whole index shipped as candidates, the agent renders four System.Version verdicts (updateAvailable/upToDate/notComparable/notInstalled), verdicts reported with the inventory mirror, admin panel "check for updates" + "updatable" badge; see docs/plugins.md and docs/api.md §4.10)
- [x] **Runtime resource declarations (medium)**. `permissions` today only determines the registration surface; network/file usage declarations could be added to the manifest, registered into load reports and audit first, without hard enforcement for now. Basis: Obsidian's `isDesktopOnly` is the minimal "declare first, review later" sample, and VS Code's `restrictedConfigurations` is the minimal declarative-restriction sample (§4.1). (✅ Landed 2026-10-09 in round 61: the manifest gains an optional `resources` array (network/filesystem/process, lower-cased and deduped, unknown values rejected at load), pure registration with no enforcement — mirrored end to end in plugin_list and every plugin_* output, CP per-agent inventory, GET /v1/plugins/installed, and the admin panel's res badge; the five official plugins GameData/MarketWatch/GameAccess/MobileAuthenticator/Monitoring led by declaring network; see docs/plugins.md §Runtime resource declarations)
- [x] **Provenance verification upgrade (medium)**. Add publisher fingerprint or signature fields to index entries, upgrading "pinned digest" to "pinned provenance". Basis: Grafana has required signatures since 7.0 and distributes by level; unsigned is simply unsupported on the official cloud (§4.2). (✅ Landed 2026-10-13: d7f0ae5 added the `publisher` declaration (manifest + index + install reconciliation + update-check `publisherChanged` drift flag + inventory mirror + admin panel); 1b8c5df added the `signing` block (`publicKey`+`signature`, RSA-PSS over the digest as lower-case hex ASCII bytes, the agent verifies the signature after checksum and before extraction, fail-closed unless `VAPOR_PLUGIN_TRUST_KEYS` is pinned, half-declared blocks treated as undeclared, SPKI canonical comparison avoids base64 line-wrap differences, install audit records `signed`); `PluginSignatureVerifierTests` 7 + `PluginHostActionTests` integration 4+ + `PluginApiTests`/`PluginEcosystemPropertyTests` all green; see `docs/plugins.md` §Catalog reconciliation and CHANGELOG 40.10-4)
- [x] **Process/resource boundary assessment (high; assess first, build later)**. An ALC isolates only versioning and unloading; a plugin's infinite loop or runaway memory takes down the whole agent. The references are GOG Galaxy's separate processes, Grafana's standalone backend binaries, and VS Code's extension host process (§4.2). The first step is quantification, not rework: measure the resident memory and failure domains of the 6 official plugins, then decide whether processes are worth it, or step down a notch to quotas and timeout circuit breakers. (✅ Quantified and landed 2026-10-09 in round 60: the 6 official plugins hold ≈2.3MB RSS resident (managed heap only ≈45KB), so memory gives no motive for processes; the real failure-domain gap is session zombification when a plugin ignores cancellation tokens (both the per-action timeout and the 900s watchdog are cooperative cancellation, not abortable); the mechanism inventory and failure-domain matrix are in `docs/research/process-boundary.md`; process isolation is rejected as a non-goal, while poisoned-session reclamation/quotas await a decision)
